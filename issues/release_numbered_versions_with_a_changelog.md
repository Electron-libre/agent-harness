# Release numbered versions with a changelog

# Goal
A consumer pins a commit of Cardinal (`rev`) with no word of what changed since its last pin, and no version says
whether an update breaks it. Ship numbered releases (`vX.Y.Z` tags) with a `CHANGELOG.md` at the root, for Cardinal
and, through the harness, for every consumer project: a recipe prepares the release, the user pushes it.

# Findings
* Each push to `main` already creates a GitHub release `cardinal-<commit>` (`.github/workflows/release.yml`): binaries
  and their digests for `cardinal run` (BIN-3), no version, no notes. These stay as they are.
* The crate version never moved from `0.1.0` (`crates/cardinal/Cargo.toml`); the repository has no version tag.
* `cardinal update --rev <tag>` already resolves a tag and pins its commit (ADR 0002): a consumer can pin `v0.2.0`
  once it exists.
* Every commit follows Conventional Commits, checked by `just check-commit` (`AGENTS.md`): the changelog can be
  generated from the `feat` and `fix` commits and the breaking ones.
* The format of the managed content already has its own number (`FORMAT`, `cardinal-format`, ADR 0014), raised on a
  change an older `cardinal` would misread.

# Approach
Decided with the user before the issue was written: offered to every consumer, not Cardinal alone; the changelog
generated by a tool of `cardinal run`, then reread; semver, the major raised when `FORMAT` rises; the user triggers a
release, the agent proposes one when a milestone of `ROADMAP.md` becomes `done`.

1. A tool `cardinal run release <version>` (recipe `just release <version>`): from the last version tag to `HEAD`,
   writes the section of `<version>` in `CHANGELOG.md` (Keep a Changelog: Added from `feat`, Fixed from `fix`, a
   breaking section first), lists the milestones of `ROADMAP.md` it delivers, and creates the annotated tag
   `v<version>` locally. It never pushes.
2. The version: proposed from the commits (major on a breaking commit, minor on `feat`, patch otherwise), checked
   against the given one. In Cardinal, a commit that raises `FORMAT` counts as breaking. Where the version is written
   in the project's manifest (`Cargo.toml`, `package.json`...) is stack-specific: a key of `.claude/cardinal.toml`
   naming the files, or a recipe hook of the project; to choose at step 1.
3. Seed an empty `CHANGELOG.md`; `skill:update-docs` knows it is written by the tool, not by hand.
4. `ROADMAP.md` names the version that delivered each `done` milestone; `skill:issue-workflow` proposes a release
   when the last issue of a milestone closes.
5. Cardinal adopts it: its first release, the crate version raised to match.

Size: a spec, a tool with its tests, a recipe, seeds and docs; check the limit of `skill:issue-workflow` step 1 and
split (tool, then the milestone link) if it is over.

# Hints
* Check that `release.yml` does not also fire on a `v*` tag push, or that it does nothing harmful then.
* Pushing a tag is outward-facing: the tool and the recipe stop at the local tag and print the push command.
* The changelog is generated, then reread by the user before the tag: the commit subjects are written for developers,
  not always for the consumers.
* Depends on the roadmap issue for the milestone link (point 4); points 1 to 3 do not.
